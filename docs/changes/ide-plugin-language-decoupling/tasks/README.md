# 语言解耦实施任务

本目录把 S1、S2 的实现与各自最小回归放进独立任务文档，开发者可以直接打开当前任务执行，不必从总方案拼接步骤。

## 执行入口

| 阶段 | 文档 | 状态 | 说明 |
|---|---|---|---|
| S1 | [核心同步语义解耦](s1-core-sync-decoupling.md) | active | 删除 Go 成功门禁，验证仓库范围、PFI 真实失败及必要保护；实现未开始。 |
| S2 | [补偿调度与依赖清理](s2-scheduling-dependency-cleanup.md) | active | 接收 S1 结果，清理调度/依赖残留并做影响范围内回归；实现未开始。 |

最终统一验收在独立的[最终系统回归与验收](../testing/final-acceptance.md)中执行。V 是整体验收阶段，不是第三个开发子任务；所有功能检查均尚未执行。

```text
S1：实现 + S1 必要回归
  → S2：实现 + S2 必要回归 + 有交叉影响时补 S1 对应用例
  → V：最终组合代码的完整插件回归 + 兼容检查 + 必要 GUI
```

## 文档分工

[总技术方案](../technical-design.md)维护 LD-01～LD-06、架构、安全边界及共同技术决策；[总测试方案](../testing/test-plan.md)维护共享 fixture、T-01～T-07 和选例/证据规则。每个任务的具体步骤、最小回归和退出条件仅在该任务文档维护；最终命令与 GUI 操作仅在 V 文档维护。

任务正文已给出开始执行所需的上下文；先遵守仓库 `AGENTS.md`，仅在具体边界或测试数据不明确时打开关联章节，不要求每轮通读全部方案。子任务不改变总契约；发现冲突时先在同一文档变更中纠正，不能自行放宽安全或验收边界。

## 串行开发与交接

默认同一工作分支串行开发，同一个最终 PR 评审；文档数不决定 commit/PR 数。S2 从 S1 的实际结果开始，不再次删除同一段代码，也不只是为了接手而重跑所有 S1 测试。

阶段交接直接写在当前工作记录或最终回复中，包含：实际代码基线、修改范围、真实测试选择器和数量/结果、未执行项及理由、下一阶段剩余项。没有提交时明确记录工作树相对基线的差异，不虚构 commit；无需再创建一个空的验收报告文件。

S1 删除类型/签名时若必须同时调整部分 S2 调度，就在 S1 完成其原子修改，并当步运行相应回归，向 S2 说明已完成部分。不能把已知编译错误、未测的直接并发影响或真实失败留给后续阶段。

如果实际代码没有可编译且可验证的中间边界，可以合并两个开发任务；仍按两份清单核对剩余工作，最后执行 V，不引入临时 adapter、开关或恒真替身维持形式上的拆分。

## 执行限制

S1/S2 不默认运行完整插件套件、双版本 Verifier、真实 GUI 或 Desktop 全业务。实际受影响的方法/类和安全分支必须运行；筛选不可靠时扩大到直接受影响的测试类。

未在阶段执行的有效测试保留到 V，不删除、不禁用。中间推送若触发现有完整 CI，仍正常执行，不修改 workflow 或使用 skip 绕过；安装、重启、真实用户目录操作、远端写入、合并与发布仍受各自授权限制。
