## 3. 功能和可靠性问题

### R01 — P1：保留目录名称未隔离，可改写克隆仓库内容

**位置：** [`src/shared/repository-utils.ts:27–35`](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/src/shared/repository-utils.ts#L27-L35)；交叉路径为 [WorkspaceService 的目录选择校验](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/src/main/services/workspace-service.ts#L637-L749) 与 [WorkspaceFileWriter](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/src/main/services/workspace-file-writer.ts#L25-L115)。

名称规则只排除空串、`.`、`..`、路径分隔符及 NUL，没有排除 `.reqws`。RepositoryService 与 schema 使用这套规则；工作区创建按 `repository.name` 生成 clone 目标，而 manifest 固定写入 `<root>/.reqws/workspace.json`。因此名为 `.reqws` 的仓库，其工作树与 ReqWS 元数据目录是同一个目录。父目录 canonical 校验无法识别这种语义上的所有权重叠。

**触发：** 录入名称为 `.reqws` 的合法远端仓库并创建工作区；该仓库根目录包含普通、受 Git 跟踪的 `workspace.json`。克隆和分支建立完成后，manifest 原子写入会替换该文件。即使远端没有这个文件，也会把管理元数据写进该仓库工作树。macOS 默认大小写不敏感卷还需考虑 `.REQWS` 等等价名称。

最小探针使用真实本地克隆、原样名称规则，以及相同目标路径上的临时文件 rename，观察到：

```text
name = .reqws
accepted = true
repository/workspace.json == manifestPath : true
before = {"userOwned":true}
after  = {"schemaVersion":1,"id":"review-workspace"}
git status --porcelain = M workspace.json
```

这是局部路径/写入复现，不是完整应用执行。被改写的是新克隆工作树中的文件；没有证据表明远端历史或原始源仓库被删除。

**建议：** 将内部保留名称/路径与仓库目录做显式互斥，在创建、更新及工作区构建入口提前拒绝冲突，至少覆盖 `.reqws` 及平台等价名称；其他保留项如 `.git` 应一并明确政策。不要用事后清理或移动用户仓库修补。新增拒绝规则属于行为修复，不能混在纯重构中。

**回归：** 真实 Git fixture 包含受跟踪的 `workspace.json`，请求以 `.reqws` 命名创建工作区，断言在 clone/写入之前返回稳定错误；验证源码内容不变、无已发布根目录和索引残留。补名称/schema 契约及大小写变体测试；若调整跨语言 manifest 规则，同步 Kotlin fixture，不重测原生 Git 功能。

### R02 — P2：成功 stdout 的脱敏破坏 origin 身份比较

**位置：** [`git-runner.ts:140–158`](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/src/main/services/git-runner.ts#L140-L158) 及 [`run` / `getOriginUrl` / `originUrlMatches`](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/src/main/services/git-runner.ts#L289-L501)。

`run()` 不只脱敏日志和错误，也对成功的 `stdout` 统一调用 `redactGitOutput`。其中通用 URI userinfo 正则会将 `ssh://git@host/...` 改为 `ssh://<redacted>@host/...`。与此同时，[URL 校验明确将 SSH 用户名作为非秘密身份选择器予以支持](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/src/shared/repository-utils.ts#L250-L318)。`getOriginUrl()` 使用已被改写的 stdout，随后与原始合法 URL 做精确比较，必然不相等。

**触发：** 通过 `ssh://git@…` URL 创建工作区，逻辑移除仓库但保留目录，再添加同一仓库；或者复用同类 URL 的已有目录。目录与 origin 实际正确，却会报 `REPOSITORY_PATH_CONFLICT`。不应泛化为所有 SSH 都失败：SCP 风格 `git@host:path` 不经过这一 URI 正则，首次 clone 也不一定失败。

真实本地 Git 的 `remote get-url origin` 配合原样脱敏函数得到：

```text
expected: ssh://git@example.invalid/team/repo.git
raw:      ssh://git@example.invalid/team/repo.git
returned: ssh://<redacted>@example.invalid/team/repo.git
matches:  false
```

探针仅在本地设置 origin，未连接该主机。

**建议：** 区分用于机器判断的内部结果与可展示诊断；让 origin 比较使用经过适当验证但未被日志脱敏改写的值，并仅返回匹配结论或安全结果。不要简单让所有原始 Git 输出穿透到 renderer、错误 detail 或日志，也不要把严格 origin 比较改成宽松 URL 猜测。

**回归：** 对 `ssh://git@host/...` 做读取/比较与逻辑 remove→add 的行为测试，同时保留 HTTPS 凭据、Authorization、token 的脱敏负向用例和“不重写等价 URL”的现有契约。

### R03 — P2：新 feature 分支继承了默认分支的 upstream

**位置：** [`branch-service.ts:81–86`](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/src/main/services/branch-service.ts#L81-L86)。

远端没有目标 feature 分支时，代码执行 `git switch -c <feature> origin/<default>`，未显式禁用跟踪。Git 默认配置会让新 feature 跟踪 `origin/main`，而不是保持无 upstream。当前应用没有自动 push；这里不声称已经发生远端覆盖。

**真实复现：** 隔离 HOME、禁用系统 Git 配置，创建仅有 main 的本地 bare origin，clone 后执行与生产代码相同的 switch：

```text
$ git switch -c feature/review origin/main
branch 'feature/review' set up to track 'origin/main'.

$ git config --get-regexp '^branch\.feature/review\.'
branch.feature/review.remote origin
branch.feature/review.merge refs/heads/main

$ git push --dry-run
fatal: The upstream branch of your current branch does not match
       the name of your current branch.
```

`pull` 的默认上游也会是 main，而不是预期的 feature。复现所有 origin 均为临时本地路径，没有向项目远端推送代码。

**现有测试缺口：** [新建 feature 的集成测试](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/tests/integration/git-branches.test.ts#L35-L54) 只断言分支名和 HEAD 起点；同文件对已存在远端 feature 的场景才检查 upstream。问题不是这些测试无价值，而是新建分支的关键副作用没有被断言。

**建议：** 只在从远端默认分支初始化新 feature 的路径使用 `--no-track` 或等价明确策略；保留已存在 `origin/<feature>` 时的显式跟踪。修复后第一次发布 feature 仍可能需要 `push -u` 或 IDE 的相应功能，不能承诺普通无参数 push 自动成功。

**回归：** 检查新建分支的 remote/merge 配置或 `@{upstream}`，确认不跟踪 main；保留远端 feature 跟踪与已有本地 feature 不被改写的用例。用本地 bare origin 验证首次明确发布只建立 feature 引用。

### R04 — P2：clone 生命周期没有有界退出或取消路径

**位置：** [`git-runner.ts:409–427`](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/src/main/services/git-runner.ts#L409-L427)；相关为 [`run` 的定时器和租约释放](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/src/main/services/git-runner.ts#L289-L377)、WorkspaceMutationCoordinator、App 的操作弹窗。

`run` 仅在传入 `timeoutMs` 时安装定时器；clone 没有传入 options，而 fetch、ls-remote、ref 检查都配置了超时。clone 之后的 `result.timedOut` 分支并不能为本次调用建立超时机制。当前调用链也没有用户可用的 clone 取消入口。

**触发与影响：** Git/SSH/凭据辅助进程或传输长期不结束，clone Promise 不完成，工作区写队列无法释放；活动门禁正确地继续阻止更新安装，但用户也无法从这条操作路径主动恢复。此项是静态可确认的生命周期缺口，本次没有真实挂起网络 clone 的端到端实验，不把所有慢 clone 都视为故障。

**建议：** 明确 clone 的取消及超时/无进度策略。大仓库不应被机械套用短硬超时；可以保留长时间传输，同时提供取消、可配置上限或可解释的无进度超时。进程真正结束后再释放租约，不能用 Promise 超时替代子进程清理，也不能因取消而删除已发布的用户目录。

**回归：** 通过现有 spawn seam 提供永不结束的子进程，验证取消/超时升级、确认 close 后释放门禁、后续 workspace 操作可以继续；同时覆盖正常长传输和取消阶段的 staging 清理。现有 [GitRunner 门禁测试](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/tests/unit/git-runner.test.ts) 验证了 lease 保留，但不替代 clone 终止策略的测试。

### R05 — P2：广泛捕获文件系统错误，抹平“缺失”和“不可访问”

**位置：** [`workspace-service.ts:75–82`](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/src/main/services/workspace-service.ts#L75-L82)，以及 [`validateCreate` 中两处 `stat(...).catch(() => null)`](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/src/main/services/workspace-service.ts#L667-L686)。Code Humanizer：**模式 #8，严重度 3**。

`pathExists` 对任意 `fs.access` 错误都返回 false。它被用于工作区状态和操作判断，因而 EACCES/EPERM/EIO 会被表述为文件缺失；两处 stat 捕获也会将无法检查表述为父目录不存在。这样的失败信息会误导用户处理路径，而无法定位真实权限或磁盘故障。

非 root 子进程访问被禁止遍历的现存父目录，原始调用与提取 helper 的结果为：

```text
fs.access error.code = EACCES
pathExists           = false
```

这是 Linux 权限探针，不是 macOS TCC 验证；没有观察到此路径导致文件删除，不能夸大成已发生数据丢失。

**建议：** 仅将明确的不存在错误映射为 missing，其他错误保留原因并返回稳定诊断。同文件已有 `pathEntryExists` 对 ENOENT 的窄捕获，可借用错误分类方式；不能直接以 lstat 替代所有 access，因为 dangling symlink 等语义不同。

**回归：** 注入 ENOENT、EACCES、EPERM、EIO，分别断言 missing 与访问失败；对 stat 路径保留 cause/code。修复会改变错误类型和提示，属于行为修复而非无风险机械清理。

### R06 — P2：旧刷新可在较新操作后覆盖界面状态

**位置：** [`App.tsx:116–133`](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/src/renderer/App.tsx#L116-L133)；相关为 [AppShell 的刷新与主操作按钮](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/src/renderer/components/AppShell.tsx#L108-L126)。

`loadData` 每次并发读取 repositories、workspaces 和 availability，完成后无条件覆盖三组 state，没有请求代次、作废标记或统一串行化。刷新按钮在 refreshing 时禁用，并不等于所有会调用 loadData 的入口被串行化：刷新期间的增删操作及其完成后的重载仍可能重叠。

**触发：** A 刷新已取得旧列表但某个响应延迟；用户完成增删，B 重载先完成并展示新列表；A 随后完成，旧快照覆盖新状态。旧请求的 finally 也可能提前清除较新刷新的状态标志。这里影响的是 renderer 的显示和后续用户判断，不是服务端状态被直接回滚。

保留相同 Promise.all/无条件赋值关系的受控调度模型得到：

```text
B 完成后：repositories=new, workspaces=new
A 随后完成：repositories=old, workspaces=old
```

模型使用可控 Promise，不是 React/Electron 集成执行；源码上存在这类响应顺序的处理缺口，真实 GUI 时序尚未测试。

**建议：** 给整次数据加载建立 generation/token，只允许仍有效的请求写入数据、错误和 loading/refreshing 状态；变更完成后的重载应使旧请求失效。也可采用单一数据层的明确串行策略，不要只为某一个按钮加 disabled。

**回归：** 在 App 层使用延迟 Promise 渲染测试，先启动刷新、再完成增删与新重载、最后释放旧响应，断言列表不倒退且刷新标志正确；补卸载时的失效处理。

## 6. GoLand 与发布链的待验证风险（不计入 8 项问题）

这些是有源码依据的后续验证方向，不是本次已经复现的产品缺陷，也不能作为削弱安全策略的理由。

**U01：仓库存在性变化与自动 no-op。** [LoadingSnapshotReader](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/integrations/goland/src/main/kotlin/com/reqws/goland/loading/contract/LoadingSnapshotReader.kt) 的 digest 包含 binding bytes、manifest digest 和绑定目录身份，不直接包含每个仓库 availability；[ManifestReader](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/integrations/goland/src/main/kotlin/com/reqws/goland/manifest/ManifestReader.kt) 的基础 digest 来自 manifest bytes。需要沿 watcher、项目模型事件和强制 reconciliation 完整验证：保持 manifest/binding 不变，恢复缺失仓库时是否会被自动 no-op 抑制。项目服务还可能通过其他事件强制重放，本次未完成这条事件链的证明，故不判定为已确认缺陷。

**U02：项目模型更新中的同步文件读取成本。** [ManagedRootsAdapter](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/integrations/goland/src/main/kotlin/com/reqws/goland/loading/model/ManagedRootsAdapter.kt) 的 update 回调会进入 verifyTransaction，而 snapshot verification 会重新读取文件；每个移除 claim 还涉及模型检查。需要在受支持 GoLand 上测量多仓及慢磁盘下的更新耗时，不以静态代码就声称 UI 卡死，也不能为了性能删除最终所有权重验。

**U03：发布前失败与保守历史审计的可恢复性。** [Marketplace `history_decision`](https://github.com/fredgnr/reqws-desktop/blob/30ea9432efe7b9062ed68a7aa803543288f45abd/scripts/publish_jetbrains_marketplace.py#L240-L291) 对同提交/同 tag 的历史 workflow attempt 缺收据会拒绝继续。需要区分“可能 POST 但证据丢失”和“已证明从未进入提交阶段”，验证 bootstrap、早期构建失败、重跑和收据过期的操作流程。当前保守拒绝本身具有安全理由；没有核实完整工作流证据与预期政策之前，不把它改成缺收据就自动 POST。

GoLand 后续可见性验收应在 **Project 面板**检查指定仓库下的文件存在/不存在，并核对 ReqWS 自有加载状态；不使用 Find in Files 代替界面边界证据，不重复验收原生 Git、Go Modules 或其他语言能力。
