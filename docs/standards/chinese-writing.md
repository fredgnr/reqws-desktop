# 中文文档写作规范

让读者知道软件能做什么、下一步点哪里、做完会看到什么；简化句子时，不改变功能、限制和完成状态。

## 依据和适用范围

本规范参考用户指定的 [shuorenhua / 说人话 SKILL](https://github.com/MrGeDiao/shuorenhua/blob/5a9eafefe03807404135f4d2ee4f42fe61d58759/SKILL.md)，采用其“保留事实、责任主体和条件，减少无实际信息的包装语”的编辑方式。这是 ReqWS 的场景约定，不是上游 skill 的完整副本。

适用于 README、当前使用指南、索引和技术文档中的中文说明。源码、界面翻译资源、命令、错误码、路径、版本、引用和历史测试结果不是自由润色对象。修改 UI 文案必须另走项目 i18n 流程；冻结的 `docs/reference/` 和按次证据不做批量改写。

## 先判断读者在找什么

README 先讲使用场景和产品分工，再给安装、上手入口。不要一开头就让新用户读签名维护、IPC、PFI 或所有权日志。

操作指南按任务组织：**入口 → 操作 → 结果 → 必要限制**。技术文档可以保留专业术语，但首次出现时解释它在当前问题中的含义。安装、排障、开发和历史证据各有自己的位置，不把它们混成同一条必读路线。

例如，用户不需要先理解“加载契约收敛”，才能知道如何少显示一个仓库；维护插件项目模型的人则仍需要准确的契约、目录归属和检查细节。

## 怎么改句子

说清谁做什么，优先使用直接动词。不要为了显得口语化而换掉精确术语，也不要凭某个词出现次数决定它必须删除。正常句子可以不改。

| 原表达 | 面向用户的写法 | 必须保留的信息 |
|---|---|---|
| 保存成功不代表 IDE 或插件已经同步。 | “选择已保存”只说明配置写好了；是否生效，要去 GoLand 的 ReqWS 面板确认。 | 保存和 IDE 同步不是同一状态。 |
| 插件只读检查已加载仓库的 Git Directory Mappings。 | 插件会检查已加载仓库的 Git 根目录，但不会替你修改 Directory Mappings。 | 检查范围和只读限制。 |
| 逻辑移除和遗忘不会删除磁盘内容。 | 从工作区移除仓库，或移除工作区记录，都不会删除磁盘上的代码。 | 两种操作及其共同限制。 |
| 生命周期材料以局部索引为权威入口。 | 某项功能的需求、设计和测试记录放在同一目录，从该目录的 README 查找。 | 材料的位置和查找方式。 |

不要把“不会删除代码”缩成“安全”，把“尚未验收”改成“支持”，把“允许手动更新”写成“自动保持最新”，或为了句子短而删掉失败条件。也不要新增性能、效率、可靠性或兼容性承诺。

用户明确要求调整结构时，才重排和拆分内容；只要求润色时，以句内修改为主。搬走独有信息时，保留一个能找到新位置的链接。要改旧事实，先核对当前代码或发布记录，并说明与纯文字改写的区别。

## 图和文字要能对上

每张截图只回答一个主要问题。正文用界面真实名称指示操作，图中编号对应附近的步骤，图注说明应看到的结果。不能只放一张全窗口截图，让读者自己猜按钮在哪里。

截图必须来自实际运行的对应版本。原型、概念图、测试 fixture 和真实截图要明确区分。未拍的图只在交接清单登记，并在正文保留 `docs-asset` 注释；文件存在前不要加失效的图片链接。

补图时填写清楚的 alt 文本，保证缩到 GitHub 正文宽度后仍能读字。不要只靠颜色表达选中、成功或失败。隐藏私人路径、URL 和凭据时保留操作含义，不伪造状态。

GoLand 的仓库显示效果，要在普通 Project 面板展开目录和文件确认，不用 Find in Files、搜索命中数或终端目录列表代替。

## 提交前核对

先读一遍修改后的文档，尝试按步骤找到按钮；再对照原文和源码，核对主体、否定、条件、版本、路径及完成状态。删掉的独有内容必须在新位置保留，历史结论不能换成新的验收结果。

最后检查链接、旧章节入口、截图与图注、最近一级索引，并运行 `npm run docs:check`。静态检查不证明中文自然，也不证明软件操作可用；真人阅读、真实截图和运行结果分别记录。格式规则见[项目文档规范](documentation-standard.md)。
