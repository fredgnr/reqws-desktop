# 项目文档规范

本规范让需求上下文、关键决策、验证方法和交付结果可查、可维护，同时避免为每个改动机械创建一套空文档。

## 1. 信息架构

文档采用三级导航：

```text
docs/README.md
  -> 分类 README.md
    -> 需求包或文档 README.md
      -> 具体文档与资产
```

- `docs/changes/`：按需求或变更聚合生命周期材料。
- `docs/guides/`：维护面向用户和开发者的当前操作指南。
- `docs/standards/`：维护规范和模板。
- `docs/reference/`：保存冻结输入，不承载当前决策。

每个 `docs/` 子目录都必须有 `README.md`。上级索引只描述直接子项，避免在多个层级复制完整清单。索引是发现与维护机制，不是每次编辑的强制阅读顺序。

## 2. 文档状态与权威性

受管理的正文使用以下最小 frontmatter：

```yaml
---
title: 文档标题
type: requirements
status: draft
updated: 2026-08-13
---
```

`type` 可取 `governance`、`guide`、`requirements`、`technical-design`、`test-plan`、`test-report`、`delivery`。`guide` 用于按任务组织的常青说明；需求承诺、设计取舍和按次证据仍应进入对应的生命周期类型，不能用指南代替。

| 状态 | 含义 |
|---|---|
| `draft` | 正在讨论，不能作为最终承诺。 |
| `active` | 当前有效，可作为需求或实现依据。 |
| `superseded` | 已被新文档替代；必须在正文和索引中链接替代文档。 |
| `archived` | 只保留历史证据，不描述当前状态。 |

同一范围和类型通常只保留一个 `active` 文档。事实冲突时，先看状态和更新时间；实现现状还需以代码和测试复核。`docs/reference/` 中的冻结资料不要求补 frontmatter，也不得因当前实现变化而改写原文。

## 3. 命名与内容

- 除 `README.md` 和冻结参考资料外，目录、文件统一使用 kebab-case。
- 需求目录优先使用稳定工单号加简短主题；没有工单号时使用明确主题，例如 `global-settings/`。
- 不使用 `final`、`latest`、`new`、`v2-final` 等失去上下文的名称。日期只用于确实按次留存的报告或发布快照。
- 标题后的第一段用一句话说明文档解决什么问题。索引摘要也保持一句话，不复制正文。
- 指南只描述当前可执行流程；有对应需求或设计时直接链接作为依据，没有当前有效设计时明确以代码和测试复核，不复制按次测试数字或把尚未验证的能力写成已交付事实。
- 使用行内相对 Markdown 链接；索引不使用 reference-style 或 HTML 链接。移动文件时同步修正所有入链，不用反引号路径代替可导航链接。

## 4. 按需产出规则

根据实际变更判断哪些材料需要创建或更新。涉及行为、验收、安全或跨层契约时明确影响；拼写修正、已被现有契约覆盖的局部修复可以用一句话说明“无其他文档影响”，不必逐项填写五类 `create/update/none` 表。不要创建空占位文件。

| 文档 | 创建或更新的典型条件 | 可以不单独创建的情况 |
|---|---|---|
| 需求说明 | 用户可见行为、范围、非目标、业务规则或验收条件变化。 | 修复实现偏离已有有效需求，且验收语义未变。 |
| 技术方案 | 跨 main/preload/renderer/shared，或涉及 IPC、schema、持久化迁移、安全、Git/path、打包安装及重要取舍。 | 局部低风险实现，已有方案已完整覆盖。 |
| 测试方案/报告 | 需要跨层验证、人工 macOS 流程、兼容迁移、失败恢复、安全负向场景或外部证据。 | 简单回归可在需求或方案的测试章节清楚表达。 |
| 交付记录 | 发布、里程碑、安装升级、配置迁移、回滚、已知限制或对外交付范围变化。 | 尚未形成独立交付的小型内部改动。 |
| 常青指南 | 当前安装、使用、开发、排障或维护流程发生变化，且该信息需要用户或开发者按步骤执行。 | 仅有内部实现变化，现有指南仍准确且无需新增操作。 |

一份文档可以承载紧密相关的内容，按主要目的选择 `type`，并在需求包索引中明确覆盖范围。只有内容需要独立评审、执行或维护时才拆分。

## 5. 需求文档工作流

已知相关文档时直接阅读任务需要的章节；位置或权威性不明时，使用[文档总索引](../README.md)和相关分类定位。按实际影响组织工作，不把以下规则当成每次改动都必须执行的固定行程：

- 改变实现方向的需求和技术决策先于实现更新；未改变契约的修复不必先重写设计。
- 需要新的生命周期材料时，创建 `docs/changes/<需求>/README.md`，并按需使用[模板](templates/README.md)。
- 验证前明确相关范围；执行后记录可复现命令、环境、结果和未完成证据。常青指南不复制按次测试数字。
- 交付范围、迁移、回滚或已知限制变化时更新相应材料；不要为内部文字改动创建发布记录。
- 同步最近一级索引；只有直接子项或摘要变化时才向父级传播更新。
- 文档改动运行 `npm run docs:check`；代码改动按[开发指南](../guides/development-guide.md)选择检查。纯文档改动不要求额外执行完整应用测试、Gradle 或安装；现有 CI 与发布验收门禁不变。

Agent 任务的授权边界、完成条件和提示词示例见[Agent 协作指南](../guides/agent-workflow.md)。

## 6. 索引格式

索引表至少包含链接、状态和一句话说明；需求总索引再包含更新日期。状态或摘要变化也视为索引变化，必须同步。

```markdown
| 文档 | 状态 | 说明 |
|---|---|---|
| [技术方案](technical-design.md) | active | 定义状态迁移和跨进程契约。 |
```

文档新增、移动、重命名或删除后，用旧路径和主题词检查残留引用：

```bash
rg -n '<旧路径|旧文件名|主题词>' README.md AGENTS.md docs
npm run docs:check
```

## 7. 完成标准

- 相关有效文档与实现没有已知冲突。
- 每个新增或改变的文档都被最近一级索引收录，父级导航在需要时已更新。
- 本地链接有效，没有未索引的文档或资产。
- `npm run docs:check` 会校验结构、索引表、链接、命名和基础元数据；标题后摘要等语义质量仍由作者和评审确认。无法运行时说明环境缺口，不声称检查通过。
- 冻结参考资料未被当成当前决策修改。
- 交付说明概括文档和索引影响、实际检查与剩余缺口；仅在有歧义时解释未产出某类材料的理由，不强制列出无关文档清单。
