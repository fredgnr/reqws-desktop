# 项目文档规范

让需求、设计、操作方法和验证结果容易查找，也避免一次小改动就新建一套空文档。中文表达和截图要求见[中文文档写作规范](chinese-writing.md)。

## 1. 信息架构

文档按以下层级查找：

```text
docs/README.md
  -> 分类 README.md
    -> 需求包或文档 README.md
      -> 具体文档与资产
```

| 目录 | 放什么 |
|---|---|
| `docs/guides/` | 当前可用的安装、使用、开发和排障步骤。 |
| `docs/changes/` | 某项需求的背景、规则、设计、测试和交付记录。 |
| `docs/standards/` | 项目规范和按需使用的模板。 |
| `docs/reference/` | 冻结的原始输入，只用于追溯。 |

每个 `docs/` 子目录都要有 `README.md`，上级索引列出直接子项，不必重复所有下级文件。已知文件位置时直接阅读，不要求每次修改前遍历所有索引。

项目首页和指南先服务读者的任务，不把内部信息架构当成用户的操作步骤。安装、证书维护或验证记录有独立入口时，给出链接，不在首页重复整篇内容。

## 2. 文档状态与权威性

除 README、模板和冻结参考资料外，正文使用以下最小 frontmatter：

```yaml
---
title: 文档标题
type: requirements
status: draft
updated: 2026-08-13
---
```

`type` 可取 `governance`、`guide`、`requirements`、`technical-design`、`test-plan`、`test-report`、`delivery`。指南用于介绍日常操作，不能代替需求承诺、设计决策或某次测试的证据。

| 状态 | 含义 |
|---|---|
| `draft` | 正在讨论或补充，不能作为最终承诺。 |
| `active` | 当前有效；设计有效不代表全部代码已经实现。 |
| `superseded` | 已被新文档替代，正文和索引都要链接新文档，并填写 `superseded-by`。 |
| `archived` | 保留历史记录，不用于说明当前状态。 |

同一范围、同一类型通常只保留一个 `active` 文档。发生冲突时，检查状态和日期，再用当前代码、发布说明和测试记录核对实现事实。`docs/reference/` 不要求补 frontmatter，也不因软件升级而改写旧结论。

## 3. 命名与内容

除 `README.md` 和冻结资料外，目录、文件统一使用 kebab-case。需求目录优先使用稳定工单号加主题；没有工单号时使用明确主题，如 `global-settings/`。

不要使用离开上下文就无法辨认的 `final`、`latest`、`new`、`v2-final`。日期只用于需要按次保存的报告或发布快照。

标题后用一句话说明这篇文档帮读者解决什么问题，索引摘要同样只写一句。指南按当前任务写步骤；技术细节和按次结果放到对应材料，不复制测试数字，也不把未验证能力写成已交付。

有有效需求或设计时，直接链接依据；没有时说明已按代码和测试核对。修正旧事实与润色句子是两类改动，前者需要记录新的依据。

使用相对、行内 Markdown 链接；索引不使用 reference-style 或 HTML 链接。移动内容时同步入链；为旧章节保留必要的跳转入口。不要用反引号路径代替本应可以点击的文档链接。

## 4. 按需产出规则

只创建本次工作实际需要的文档。涉及行为、验收、安全或跨层约定时，说明影响；普通文字修正可以直接写“无其他文档影响”，不必填写五类材料清单。

| 材料 | 什么时候需要 | 什么时候可以不单独建 |
|---|---|---|
| 需求说明 | 用户可见行为、范围、非目标、业务规则或验收条件改变。 | 只是修复代码偏离已有需求，验收含义不变。 |
| 技术方案 | 涉及跨进程、IPC、schema、持久化、安全、Git/路径、安装或重要取舍。 | 局部低风险修复，已有方案足以说明。 |
| 测试方案或报告 | 需要跨层、人工 macOS、迁移、失败恢复、安全负向或外部证据。 | 简单回归能在现有测试章节交代清楚。 |
| 交付记录 | 发布、里程碑、安装升级、迁移、回滚或对外交付范围改变。 | 还没有独立交付的内部小改动。 |
| 使用或开发指南 | 日常安装、使用、开发、排障或维护步骤改变。 | 内部实现变化不影响已有操作。 |

紧密相关的内容可以放在同一文档，按主要用途选择 `type`，并在需求包 README 中说明。只有需要分别评审、执行或维护时才拆开，不创建空占位文件。

## 5. 需求文档工作流

直接阅读与任务有关的章节；位置或状态不明时，再查[文档总索引](../README.md)。

改变实现方向的需求和设计，先于代码更新。没有改变约定的修复，不必先重写设计。需要新材料时，建立 `docs/changes/<需求>/README.md`，再按需使用[模板](templates/README.md)。

验证前写明范围，验证后记录可复现命令、环境、实际结果和未完成项。日常指南不重复按次测试数字。发布、迁移、回滚或已知限制变化时更新相应记录；不要为文字修改新建发布记录。

同一次修改中更新最近一级索引；只有直接子项或摘要变化时，才继续更新上级。运行 `npm run docs:check`；代码检查按[开发指南](../guides/development-guide.md)选择。纯文档修改不额外要求完整应用测试、Gradle 构建或安装，但也不关闭已有 CI 和发布检查。

Agent 的权限、完成条件和提示词示例见[Agent 协作指南](../guides/agent-workflow.md)。

## 6. 索引格式

索引表至少包含链接、状态和一句话说明；需求总索引再加更新日期。正文状态或索引摘要改变时，一起更新。

```markdown
| 文档 | 状态 | 说明 |
|---|---|---|
| [技术方案](technical-design.md) | active | 定义状态迁移和跨进程契约。 |
```

新增、移动、重命名或删除文件后，用旧路径和主题词检查残留引用：

```bash
rg -n '<旧路径|旧文件名|主题词>' README.md AGENTS.md docs
npm run docs:check
```

截图等资产也要收录到最近一级索引。尚未制作的图片只在清单中记录计划路径，不创建失效图片链接或空图片文件。

## 7. 完成标准

改过的现行文档应与代码和发布范围一致，并能从最近一级索引找到。链接、文件名大小写、元数据和状态要正确；移动过的内容不能留下失效入口。

`npm run docs:check` 检查结构、索引表、链接、命名和基本元数据，不检查中文是否自然、章节锚点是否准确或截图是否符合当前界面。这些仍需人工阅读和验证。无法运行时写明原因，不把未执行记成通过。

不改写冻结输入或旧验收结论来证明新版本。交付时说明改了哪些文档、实际检查了什么、还缺什么；没有歧义时，不必逐类列出本次无关的材料。
