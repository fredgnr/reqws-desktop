# 项目文档规范

本规范让需求上下文、关键决策、验证方法和交付结果可查、可维护，同时避免为每个改动机械创建一套空文档。

## 1. 信息架构与按需阅读

文档按总索引、分类、需求包及正文分层导航，但不要求每次编辑顺序通读各层。

- `docs/changes/`：按需求或变更聚合生命周期材料。
- `docs/guides/`：维护面向用户和开发者的当前操作指南。
- `docs/standards/`：维护规范和模板。
- `docs/reference/`：保存冻结输入，不承载当前决策。

已知目标时直接阅读相关章节；领域或权威性不明时使用[总索引](../README.md)、相关局部索引或关键词搜索。不要把文档发现流程变成所有任务的前置审批。每个 `docs/` 子目录仍必须有 `README.md`，上级索引只描述直接子项，不复制完整叶子清单。

## 2. 文档状态与权威性

受管理的正文使用以下最小 frontmatter：

```yaml
---
title: 文档标题
type: requirements
status: draft
updated: 2026-08-13
---
```

`type` 可取 `governance`、`guide`、`requirements`、`technical-design`、`test-plan`、`test-report`、`delivery`。`guide` 按当前任务组织；需求承诺、设计取舍和按次证据不能用指南代替。

| 状态 | 含义 |
|---|---|
| `draft` | 正在讨论，不能作为最终承诺。 |
| `active` | 当前有效，可作为需求或实现依据。 |
| `superseded` | 已被新文档替代；必须在正文和索引中链接替代文档，并提供 `superseded-by` 元数据。 |
| `archived` | 只保留历史证据，不描述当前状态。 |

同一范围和类型通常只保留一个 `active` 文档。事实冲突时先看状态和更新时间，再以代码和测试复核实现现状；不要悄悄选择方便的版本。`docs/reference/` 中冻结资料不要求补 frontmatter，也不得因当前实现变化而改写原文。

## 3. 命名与内容

- 除 `README.md` 和冻结参考资料外，目录、文件使用 kebab-case。需求目录优先使用稳定工单号加简短主题；没有工单号时使用明确主题。
- 不使用 `final`、`latest`、`new`、`v2-final` 等含混名称。日期只用于按次留存的报告或发布快照。
- 标题后的第一段用一句话说明文档解决的问题；索引摘要也保持一句话，不复制正文。
- 指南只描述当前可执行流程，链接对应需求或设计而不复制决策与按次测试数字；没有 active 设计覆盖的现状以代码和测试核实，不把未验证能力写成已交付事实。
- 使用行内相对 Markdown 链接；索引不使用 reference-style 或 HTML 链接。移动文件时同步修正入链，不用反引号路径代替导航。

## 4. 按需产出规则

按变更影响选择材料，不按固定仪式产出。需求、跨层设计、验收条件或交付边界变化时，明确受影响材料是创建、更新还是无需变化；会决定实现方向的需求与技术决策在编码前确定。局部修复、纯格式或错字更正可只更新现有文档，并用一句话说明无额外文档影响，无需五类逐项报告。

| 文档 | 创建或更新的典型条件 | 可以不单独创建的情况 |
|---|---|---|
| 需求说明 | 用户可见行为、范围、非目标、业务规则或验收条件变化。 | 修复偏离已有有效需求的实现，验收语义未变。 |
| 技术方案 | 跨 main/preload/renderer/shared，或涉及 IPC、schema、迁移、安全、Git/path、打包安装和重要取舍。 | 局部低风险实现且已有方案完整覆盖。 |
| 测试方案/报告 | 需要跨层验证、人工 macOS、兼容迁移、失败恢复、安全负向场景或外部证据。 | 简单回归可在现有文档的测试章节表达。 |
| 交付记录 | 发布、里程碑、安装升级、配置迁移、回滚、已知限制或对外交付范围变化。 | 未形成独立交付的小型内部改动。 |
| 常青指南 | 安装、使用、开发、排障或维护流程变化，需供人重复执行。 | 内部实现变化但现有操作仍准确。 |

`none` 是合法结论，不创建空占位文件。一份文档可以承载紧密相关的内容，按主要目的选择 `type`，在需求包索引中说明覆盖范围；仅在内容需独立评审、执行或维护时拆分。[模板](templates/README.md)按需使用，不必全部加载。

## 5. 更新与验证

材料在同一变更中与行为保持一致：按需定位，确定影响，更新必要内容，记录真实验证结果，再同步导航。新增需求包使用 `docs/changes/<需求>/README.md` 聚合实际需要的材料。保留无关工作区修改；只读解释或评审不隐含文档写入授权。

文档新增、移动、重命名、删除，或状态/摘要变化时，同步最近一级索引和受影响入链。直接子项或分类摘要变化才逐级更新父索引，不为每个正文改字改动整条索引链。

文档修改后运行 `npm run docs:check` 并修复引入的问题。纯文档/指令修改还应校验改动的 skill 引用、元数据和 eval JSON，但不因编辑 Markdown 就要求本地 Electron 打包、完整 Vitest 或 Gradle。涉及代码时，按[开发指南](../guides/development-guide.md)运行对应门禁；现有 CI、发布和人工验收要求不变。环境缺失时明确记录未执行项，不能写成通过。

## 6. 索引格式

索引表至少包含链接、状态和一句话说明；需求总索引再包含更新日期。状态或摘要变化也属于索引变化。

```markdown
| 文档 | 状态 | 说明 |
|---|---|---|
| [技术方案](technical-design.md) | active | 定义状态迁移和跨进程契约。 |
```

移动或删除文档后，可按旧路径、文件名和主题检查残留引用，再运行文档检查；不要求在所有无关任务中执行全库搜索。

## 7. 完成标准

相关 active 文档与实现没有已知冲突；需要变化的最近一级索引、父级导航和入链已同步；本地链接、命名和元数据有效；冻结参考资料未改写。完成必要更新与检查后交付，不停在文档大纲。

`npm run docs:check` 校验 `docs/` 结构、索引表、链接、命名和基础元数据，以及根 README/AGENTS 的链接；它不遍历 `.agents/skills/`，也不验证语义质量或 skill 的实际触发行为。后者另按[Agent 协作指南](../guides/agent-workflow.md)检查。

最终交付说明列出实际文档变化、检查结果和重要证据缺口；只有存在容易误解的范围排除时才展开说明未产出的其他材料。
